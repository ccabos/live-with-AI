# More Code, Not Fewer Coders

*Why cheap AI code will multiply software developers, not replace them.*

The software developer is supposed to be the textbook casualty of this revolution. The machines can
write code now — fluently, quickly, for the price of a little electricity — and writing code is, on
its face, the whole job. If the work is producing software and a model produces software, the
conclusion looks like it writes itself: the developer is automating themselves out of existence,
faster than anyone, because they are building the very thing that replaces them.

I think this conclusion is not just wrong but close to backwards, and it is worth saying exactly
why, because the reasoning that saves the developer is the same reasoning that should be applied to
everyone else — only in the developer's case the evidence is unusually clear and unusually hopeful.

Start with what is true in the fear. Producing code — turning a known intention into working syntax —
is exactly the kind of cognitive work the machines now do well, and its wage-value, *as* typing,
is falling toward the cost of the compute that does it. But the typing was never where a developer's
value actually lived. The value was always in the things wrapped around the code: deciding *what* to
build, judging whether what got built is actually right, owning the system when it fails at three in
the morning, holding the whole architecture in one mind. Capability — the raw production — migrates
to the machine. Value migrates too, but it migrates *upward*, toward judgment, taste, and
accountability, which a model cannot hold because it cannot be the one who answers for the result.

That much is a story about survival. The developer's real story is better than survival, and it has
a name.

## Jevons's paradox

In 1865 the economist William Stanley Jevons noticed something strange about coal. Everyone assumed
that as steam engines grew more efficient — wringing more work from every lump of coal — Britain
would burn less of it. The opposite happened. Efficiency made coal-power cheaper; cheaper power
found a thousand new uses no one had bothered with before; and total coal consumption soared. This
is Jevons's paradox: when you make something dramatically cheaper to use, you do not use less of it.
You find vastly more uses for it.

Code is about to get radically cheaper to produce. The naive forecast — less code to write, so fewer
people to write it — assumes the world's demand for software is a fixed quantity that we are about to
satisfy with less labor. That assumption is false, and four pieces of history show why.

**The compiler.** This is the most on-the-nose precedent we have, because it is the developer's own.
We do not hand-write machine code anymore; the compiler does it. We do not manage memory by hand;
the runtime does it. Every one of these leaps automated what had been the hard, skilled core of
programming, and made a single programmer many times more productive. By the fixed-demand logic, each
should have shrunk the profession. Instead the profession exploded — from a tiny priesthood of
thousands into tens of millions — because cheaper software meant more software was worth building.
AI is simply the next and largest abstraction layer in that exact sequence. By the only precedent
the field has, it grows the field.

**The spreadsheet.** In 1979, VisiCalc automated the thing accountants did all day: recompute the
ledger by hand, cell by cell. The bookkeeping clerks who only did the arithmetic did dwindle. But the
number of accountants and financial analysts *grew*, because once modeling a budget took minutes
instead of weeks, everyone wanted it done — for every scenario, every department, every what-if. The
drudgery vanished and the judgment work it had been hiding multiplied. That is the developer's future
in one image: the machine takes the recalculation, and you get the modeling.

**The cloud.** A decade ago, standing up a server meant procurement, hardware, and weeks of waiting.
Now it is an API call and a few seconds. This did not shrink the people who run infrastructure; it
exploded into entirely new professions — DevOps, site reliability, platform engineering — because
near-free infrastructure invited an avalanche of new services, every one of which someone has to
design, operate, and answer for.

## Why software, especially

Jevons's paradox is not a law of nature. It needs one condition to favor workers rather than replace
them: the demand for the cheapened thing has to be far from satisfied — there has to be a great reservoir of
unmet want waiting for the price to fall. Software meets that condition more completely than almost
anything else in the economy.

Every organization on earth is sitting on a backlog of software it wants and cannot afford. The
internal tool never built, the integration nobody had time for, the test suite never written, the
clumsy legacy system never modernized, the small idea that was never quite worth a team's quarter.
The appetite for software has never been the bottleneck. The *cost of building it* has. Lower that
cost by an order of magnitude and the backlog does not stay a backlog; it converts into work. The
world does not want a fixed amount of software that we are about to finish. It wants vastly more than
it has ever been able to pay for, and we are about to make it affordable.

## What the developer becomes

So the role does not shrink. It grows — and it grows in the direction of the most human and most
satisfying parts of the craft. The leverage of a single judging mind multiplies: you stop being the
person who types the function and become the one who decides what is worth building, directs a fleet
of agents to build it, judges what they produce, and owns the result. Less of the day is syntax;
more of it is taste, systems thinking, and the hard question of whether a thing is right. The work
migrates up the stack toward architecture, judgment, and accountability — which is to say, toward
exactly the parts that were always the most valuable and the hardest to automate. The developer
becomes, in a literal sense, a director of machine intelligences, commanding more capability than a
whole team once did.

None of this is automatic or painless, and it would be dishonest to pretend otherwise. The junior
rung — the boilerplate and the well-specified function, the work an apprentice once cut their teeth
on — is the first to be automated, and that breaks the ladder by which people used to climb to the
judgment the top rewards. We will have to build new ladders deliberately. But notice that this is a
problem of *how the expansion is shared*, not *whether it happens*. The aggregate direction, for
once, points up.

The coal did not run out when the engines grew efficient; Britain built an industrial economy on the
demand that efficiency unleashed. Make code cheap and we will not build less software. We will
finally build the mountain of it we have been putting off for decades — and someone still has to
decide what to build, and whether what got built is any good. Of all the workers this age will
unsettle, the developer is not the most threatened. They are the most amplified: the one whose reach
grows fastest, holding the tools that make everything cheaper — including their own most valuable
judgment, which is the one thing the machine still cannot supply.
